# 分区路由 · Partition Router

两个半边，一块看板。

**宿主侧（`dsh-host-router`）**：声明式的*文件分区*——名字、绝对根目录、
include/exclude glob、把自由文本路由到该分区的关键词、worker 并发数、验收命令表。
一条需求只会落到一个分区（按显式分区名、按涉及的文件、按文本关键词、或按配置的默认分区；
证据打平就报错，不猜）。一个 worker 就是真实挂在 Harness 里的 subagent 会话，工作目录即分区根。

**客户端侧（`dsh-client-ui-router`）**：右侧栏面板，列出所有分区、每个分区的 manager 与 worker，
以及所有任务，按「人能对它做什么」分成：进行中、排队中、已结束。

## `reported` 不等于 `verified`

这是整块看板存在的理由。worker 的收尾消息只是一句*声明*，它把任务推进到 `reported`，
面板把它单独渲染成一条泳道（待验收）。只有**另一个独立的裁决**才能把任务推进到 `verified`
——验收命令通过，或者人在面板上按下「通过验收」。这两个状态永不合并，
也不允许任何自动化跳过中间状态。

## 面板能做什么

- 用纯文本发布需求；分区由宿主判定，并回报判定理由。
- 读每个 worker 的工作清单——从该 worker 自己 Session 的 `todo/write` 事件折叠而来，
  含当前正在做的那一步。
- 对待验收任务做「通过 / 退回」，退回要写原因。
- 启用 / 停用一个分区；停用后不再接受新需求。

## 两个半边怎么通信

面板跑在浏览器里，调不到宿主进程的服务，所以宿主把同一份事实发布成一小套**同源 HTTP 接口**
（`/api/router/*`），注册在本来就在伺服 Web 外壳的 Harness web server 上。
没有新传输层、没有新的声明格式、浏览器里不出现任何凭据。

## 配置

分区根目录必须是绝对路径；`workers` 是分区内并发；`verify` 是验收命令表。
没有验收命令的分区只能到 `reported`，直到有人裁决——这是受支持的状态，不是缺陷。

两个半边之间的线上契约、确切的状态映射、以及全部端点清单见
[INTEGRATION.md](INTEGRATION.md)。
